## C# rules that produce the warning

Source links below refer to the pinned checkout, not a moving upstream branch.

1. **ComponentValidation is an archive/destination checker, not execution.** `Run()` calls `VerifyExtractPaths()` then `ParseDestinationWithAction()` ([ComponentValidation.cs:42](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ComponentValidation.cs:42)). Archive candidates come only from applicable Extract instructions, including immediate option instructions ([191](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ComponentValidation.cs:191)). If no archives are found, the checker adds `Missing Required Archives` for top-level Extract instructions and returns; it does **not** check loose Copy/Move source existence ([74](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ComponentValidation.cs:74)). A Copy-only component therefore passes this stage if destination validation succeeds.

2. **Available archives change component checking.** With archive candidates, non-Extract/non-Choose sources are checked for membership; missing members and unreadable/invalid archives can add errors ([394](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ComponentValidation.cs:394)). Sources rooted at either game placeholder bypass archive membership checking ([133](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ComponentValidation.cs:133)). Copy/Move destinations normally must be valid existing directories; absent destination is an error ([331](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ComponentValidation.cs:331)). `AttemptFixes` can mutate definitions/create destination directories in C#; this is not permission to add writes to Rust validation.

3. **Instruction execution resolves source availability at execution time.** Extract, Copy, and Move use `TryResolveInstructionSourcesAsync`; failure returns `FileNotFoundPre` ([ModComponent.cs:1575](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ModComponent.cs:1575)). The resolver first uses current provider state, then catches FileNotFound/wildcard-no-match and attempts registry-backed auto-extraction and, for Move, a subfolder-variant remap ([975](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ModComponent.cs:975)). Registry auto-extraction needs a unique matching registered archive that exists through the provider; ambiguous matches do not authorize picking an archive ([1367](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ModComponent.cs:1367)). Thus a raw missing path is not always an unavailable instruction source: preceding virtual operations or established resolver rules may supply it.

4. **The component exits on the first failed instruction.** `FileNotFoundPre` or `FileNotFoundPost` becomes `MissingSourceFiles`, and the remaining instructions in that component are not executed ([ModComponent.cs:1829](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ModComponent.cs:1829)). Other non-success returns become an error/cancellation outcome. This is an execution outcome, not an error-message substring classification.

5. **The dry-run orchestrator gives that outcome one warning per component.** On `MissingSourceFiles`, it removes new VFS issues collected since the component began, appends `Warning / DryRunSkipped / Skipped '<name>' during dry-run: source archives or files are not available.`, and proceeds to the next selected component ([DryRunValidator.cs:498](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/Services/Validation/DryRunValidator.cs:498)). The warning sets AffectedComponent, but no instruction/path fields. It does not roll back earlier virtual writes within that component. Unknown failures and exceptions remain errors. It is incorrect to turn every low-level `CopyFile`/`MoveFile` issue into a warning: the VFS methods themselves still emit errors when invoked with a missing source ([VirtualFileSystemProvider.cs:562](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/Services/FileSystem/VirtualFileSystemProvider.cs:562), [648](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/Services/FileSystem/VirtualFileSystemProvider.cs:648)).

6. **A warning-only dry run remains valid.** IsValid excludes Error/Critical, not Warning ([DryRunValidationResult.cs:24](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/Services/Validation/DryRunValidationResult.cs:24)). The pipeline counts the dry warning rather than incrementing its passed-stage count ([InstallationValidationPipeline.cs:175](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/Services/Validation/InstallationValidationPipeline.cs:175)). With five other clean stages this explains exactly 0/1/5. Missing archive errors in ComponentValidation still make the overall report fail even when DryRun is warning-only.

7. **C# full-report Conflicts does not simulate Copy.** It examines declared component Dependencies and Restrictions, emitting dependency warnings and restriction errors ([InstallationValidationPipeline.cs:293](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/Services/Validation/InstallationValidationPipeline.cs:293)). A missing loose file does not fail this stage. Rust's separate simulated-write conflict API has a different purpose and must retain its existing contract.

## Actual installation remains protected

C# real installation runs the same instruction sequence with `RealFileSystemProvider`, marks success only for Success, and by default marks a missing-source outcome Failed ([ModComponent.cs:867](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/ModComponent.cs:867)). The batch service breaks on failure and blocks descendants ([InstallationService.cs:1319](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/Services/InstallationService.cs:1319)). Explicit C# `ContinueInstallOnMissingSources` and `ContinueInstallOnModFailure` options exist, default false ([MainConfig.cs:144](/home/brunner56/.codex/worktrees/5813/ModSync/src/ModSync.Core/MainConfig.cs:144)); they are not authorized Rust behavior. C# may already have performed earlier writes before a later missing instruction, and its Move fallback is broader than Rust's receipt-verified model. A warning report is therefore not proof that a real install will succeed.

Rust's stronger install protection must stay intact: [engine.rs:563](../../src/engine.rs#L563) takes the lock, checks pending state, scans and verifies completion, runs strict nonmutating preflight, rescans, then creates recovery snapshot and enters actual execution. Missing-source classification for **report generation** must not make this preflight succeed, skip an actual component, create a receipt, replay completed work, or backfill a failure. Existing normal `validate()` and standalone `conflicts` behavior need not be weakened to match a distinct structured report stage.
