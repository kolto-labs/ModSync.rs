## Three distinct C# storage mechanisms

They must not be conflated into one functioning install integration.

**A. Install-session state plus latest ZIP backup.** `Core/Services/Checkpoints/CheckpointPaths.cs:21–48,58–78` defines `<game>/.modsync/install_session.json`, `last_good_backup.zip`, and `checkpoints/`. `CheckpointManager.InitializeAsync:78–109` reads existing state, accepts it if ComponentOrder and Components are non-null (`:339`), and syncs component states/timestamps by GUID (`:280`); no definition/hash/root/order equivalence check occurs at that boundary. New sessions use version `2.0`.

`Core/Installation/InstallSessionState.cs:14–67` serializes PascalCase Version, SessionId, CreatedUtc, DestinationPath, ComponentOrder, Components, BackupPath, CurrentRevision, BaselineCheckpointId and ComponentCheckpoints. Each entry contains ComponentId, enum State, LastStartedUtc and LastCompletedUtc. CompletedComponents is computed, not serialized. Default Newtonsoft settings (`CheckpointPaths.cs:65`) mean enum values need actual serialization proof rather than guessed string encoding. Save uses temp write + overwrite-copy + delete (`:111–130`), not an atomic rename transaction. EnsureSnapshot reuses an existing ZIP (`:193`); PromoteSnapshot replaces it after a successful component (`:211`). RestoreSnapshot extracts ZIP, deletes game contents except `.modsync`, and copies back (`:236–278`), without a hash-verified manifest. A call-site search over Core/GUI found its declaration only: do not infer automatic rollback from the public method.

**B. Git checkpoint history, wired into installation.** `Core/Installation/InstallCoordinator.cs:35–90` initializes manager/session, ZIP baseline and Git service unless NoCheckpoint; even NoCheckpoint still initializes the session manager. Git service uses `<game>/.modsync/checkpoints` as its working tree and `.git` beneath it (`Core/Services/GitCheckpointService.cs:35–76`). Baseline creation reuses current HEAD when history exists (`:351`), rather than locating a separately immutable initial commit.

`GitCheckpointService.cs:83,166,221,254,268,293` exposes create, restore, list, current, clear-all and diff plus created/restored/progress events. Create copies game files excluding `.modsync`, stages and commits; empty changes reuse HEAD. Commit messages encode index/total/name/GUID/author/time (`:443`). Restore force-checks out the commit, deletes game files absent from the restored working tree and copies the latter back (`:166–214,404–442`). **Source risk requiring a probe:** sync-to-Git only copies existing game files and does not remove stale working-tree paths (`:380–402`), so a game deletion may fail to become a Git deletion. Do not copy this behavior as intended parity.

**C. Immutable CAS/session API, separate from the wired Git install path.** `Core/Services/ImmutableCheckpoint/CheckpointService.cs:21–95` constructs storage and starts a new session; `:95–214` creates deltas with every tenth checkpoint an anchor. Public methods include restore (`:217`), complete (`:361`), list checkpoints/sessions (`:388,393`), delete session (`:429`), GC (`:446`), validate checkpoint/session (`:714,767`) and repair (`:786`). Restore depends on in-memory `_currentSession`, current counter and files (`:225–252`); there is no public reopen/resume-session method in this class. A source call-site search over Core/GUI found no calls to its StartInstallationSessionAsync or CreateCheckpointAsync beyond declarations; the normal installer creates Git checkpoints instead.

CAS layout is `checkpoints/objects/<first2 hash>/<remaining hash>` holding full uncompressed file/stream bytes (`ContentAddressableStore.cs:69–106,257–267`). Sessions are `checkpoints/sessions/<id>/session.json`, `baseline.json`, and `checkpoints/<checkpoint-id>.json` (`CheckpointService.cs:585–631`); JSON writes directly truncate (`:642`). `BinaryDiffService.cs:24–120` stores source/target bytes plus bidirectional deltas, using `full_copy` or `octodiff`; exact Octodiff byte interoperability needs executable reference fixtures.

`FileProvenance.cs` schema inventory:

- FileState (`:11`): Path, Hash, CASHash, Size, LastModified.
- Checkpoint (`:25`): Id, SessionId, ComponentName/Guid, Sequence, Timestamp, PreviousId, IsAnchor, PreviousAnchorId, Files map, Added paths, Modified deltas, Deleted paths, TotalSize, DeltaSize, FileCount.
- FileDelta (`:62`): Path, Source/TargetHash, Source/TargetCASHash, Forward/ReverseDeltaCASHash, Source/TargetSize, Forward/ReverseDeltaSize, Method.
- CheckpointSession (`:89`): Id, Name, GamePath, StartTime, EndTime, CheckpointIds, IsComplete, TotalComponents, CompletedComponents.

## Actual install, failure and browser behavior

`Core/Services/InstallationService.cs:1214–1332` loads session state and selected ordered components; Completed entries skip execution, and Skipped/Blocked entries also skip. Component execution updates state; success attempts a Git checkpoint, **catches checkpoint errors as warnings**, then promotes ZIP and finally saves session. Failure normally marks dependent descendants blocked, saves and breaks. Continue-on-missing/continue-on-failure branches advance to later components without restoring the failed step. Cancellation/exception timing and the gap between filesystem effects, checkpoint, ZIP and session save need production failure probes. The source does not establish a transactional checkpoint boundary. `ModComponent.cs:852,900–961` changes Running/Completed/Blocked/Skipped/Failed in memory; the service persists after the call, not before every instruction.

Two GUI routes differ:

- `GUI/Dialogs/WizardPages/BaseInstallCompletePage.axaml.cs:205` opens GitCheckpointBrowserDialog. The dialog lists current/history, shows diff groups, confirms restore and directly invokes Git restore (`GitCheckpointBrowserDialog.axaml.cs:63,138,269–306`). Listing auto-initializes Git and may create baseline (`GitCheckpointService.cs:221–259`), so it is not necessarily read-only. Restore does not reconcile install_session states in the inspected dialog/service path; a stale Completed set after rollback is an explicit probe/contract concern.
- `GUI/MainWindow.axaml.cs:6003` opens CheckpointManagementDialog, which instantiates immutable CheckpointService (`dialog:51`), lists sessions/checkpoints/storage, exposes rollback and cleanup. Cleanup deletes completed sessions and runs GC (`:314–351`). **Its rollback calls `InstallationCoordinatorService.RestoreToCheckpointAsync` (`dialog:274`), which only logs “checkpoint system disabled” and returns (`Core/Services/InstallationCoordinatorService.cs:194–204`).** The dialog subsequently reports success; that is disabled wiring, not functioning restore evidence. That coordinator also returns empty available sessions and has a no-op rollback (`:177–204`); its misleadingly named ExecuteComponentsWithCheckpointsAsync creates no checkpoints and can continue after some failures (`:28–169`).

The inspected C# CLI exposes `--no-checkpoint` and failure-continuation switches (`Core/CLI/ModBuildConverter.cs:625,3294–3313,3396`), not a demonstrated complete checkpoint CRUD CLI. Rust agent/native action parity still requires shared operations accessible outside UI; exact new command naming is a design decision, not a C# alias to invent.

## Missing contracts and decisions for the implementation plan

1. **Durable component boundary:** define after-success checkpoint publication and before-next-component invariant across game, mod workspace, deployment manifests, session and completion receipts. Preserve one checkpoint before the first component and a verified successful prefix. A component checkpoint failure must stop advancement under the user’s fail-closed rule, unlike C# warning-and-continue.
2. **Resume identity:** bind roots, guide definitions, selections/options, ordered prefix, source mutations and external patcher outputs. C# GUID-only session sync is insufficient. Restore the pre-failure checkpoint, verify content, retry failed N, then replay N+1 onward. Never skip/backfill; do not let imported Skipped/Blocked or stale Completed authorize continuation.
3. **Storage/interoperability:** choose one authoritative Rust session backend and explicitly define import/export for C# session JSON, Git history and immutable JSON/CAS/deltas. Supporting all exposed F11 functionality does not require wiring two authoritative install engines. Byte-level Git/Octodiff compatibility cannot be assumed from equivalent file results. Keep foreign untrusted paths/content fail-closed and avoid overlapping Git and CAS storage accidentally.
4. **Root coverage:** C# mechanisms capture game state, whereas Rust restores both game and mod trees. Retain mod-root restoration for destructive Move/Extract flows; a game-only resume can make retry impossible. Define archives excluded from CAS only when recoverability is proven, not for space savings alone.
5. **Restore semantics:** named successful checkpoints, baseline, restart/reopen, changed/tampered/missing objects, interrupted restore and later-history branching must be explicit. After restore, atomically reconcile session prefix and completion evidence; pending failure stays fenced until verification succeeds. Do not replicate the immutable-dialog no-op success or Git deletion omission.
6. **Lifecycle/concurrency:** locks, cancellation during copy/hash/commit, process kill, disk-full, garbage-collection reachability, retention/deletion, provenance and storage budgets need shared contracts. No crash-durability claim from file rename alone. An allowed `--no-checkpoint` policy and C# best-effort aliases need explicit compatibility decisions; the current user no-skip/no-backfill rule remains controlling.
7. **Presentation:** history/session/file changes, current boundary, progress, restore/repair/delete/GC and accurate errors belong to shared services used by CLI and GUI. Completion cards must report actual checkpoints; preserve existing Base/Remaining receipts and failed-run captured-root behavior.

These are decisions to record and resolve in the plan, not an automatic new user-permission gate. Clear safety requirements are already authorized; policy ambiguities must not be silently converted into reduced scope.

## Smallest serialized implementation/proof sequence

1. **Reference fixtures and contract:** drive pinned production services on disposable trees to capture session/CAS JSON, enum/date encoding, Git deletion/restore behavior, stopped install state, and immutable no-op UI routing separately. Define supported interop levels and the safety deviations above; bind source/DLL bytes. No Rust harness.
2. **Read-only session/history model:** implement shared validated schema/path/object readers plus list/inspect/diff/provenance operations; expose production CLI. Cross-read C# artifacts without installing or restoring yet. Reject corrupt/traversal/root-mismatch inputs before mutation.
3. **Durable checkpoint storage:** implement baseline/component capture, verified objects, atomic session boundary, retention and recovery after interrupted writes. Preserve current whole-run fallback during transition. Probe disk/corruption/cancellation and actual created/deleted/changed files; serialized build owner only.
4. **Engine resume/restore integration:** create successful per-component boundaries in actual run_ordered, fence failure, restore previous boundary and replay exact suffix. Probe process interruption before/after each publication boundary, destructive mod-root actions, Choose, patcher effects, Base/Remaining, managed-deployment state and changed input rejection. Completion is emitted only after durable agreement.
5. **Git/immutable interop and lifecycle:** finish required import/export, delta validation/repair, history branching/deletion/GC with executable cross-runtime fixtures; do not promote API-shaped stubs. Keep disconnected C# reference behavior labelled as such while implementing real required Rust capability.
6. **Native browser + full acceptance:** add shared CLI/native session/history controls and accurate completion/status fields; run pointer/keyboard restore/restart flows with exact bytes and ordered replay. Then F29 remains mandatory: isolated K1/K2 C#/Rust/manual comparisons in guide order and live-game proof. Tiny checkpoint fixtures do not close it.

Each implementation task gets fresh implementer, specification review, then independent quality review. No competing source writers or builds. The Rust-test freeze and protected live roots remain unchanged.
