# Safe component checkpoints, restart and history

Status: independently approved implementation contract, 2026-09-28. Scope F10/F11 and their F18/F24/F26 integration; neither domain is complete. Evidence: [checkpoint source audit](checkpoint-source-audit.md), [acceptance](ACCEPTANCE.md), current `recovery.rs` and `engine.rs`. C# reference remains `d31ccbd3`. This plan makes routine design decisions; it does not introduce a user-approval gate.

## Binding outcomes and compatibility policy

- Persist a baseline and every successful top-level component boundary. Failed/cancelled N cannot advance. Restore the boundary before N, verify both roots, then retry N and replay the ordered suffix. Nested Choose stays within its owning top-level component transaction; no independent option checkpoint that changes guide order.
- Provide real list/inspect/provenance/diff, selected restore, restart/resume, validation/repair, retention/delete/GC and native history browsing. CLI and desktop share one service. Never reproduce C# immutable-dialog no-op restore followed by success.
- Use **one authoritative Rust immutable full-manifest/CAS backend**. Reusing content objects gives deduplication without requiring binary deltas for correctness. Required public outcomes are per-component history, content-addressed bytes, provenance, correct restore/resume and browsing. [ACCEPTANCE.md F11](ACCEPTANCE.md) says “Per-component Git/immutable checkpoints, content-addressed data, provenance, restore/resume, browser UI”; its proof gate is interrupted-boundary resume, hashes/order and desktop/CLI browse/restore. It does **not** state checkpoint import/export, identical Git IDs, compressed objects, timestamps or bidirectional format conversion. Those must not become mandatory closure criteria by inference.
- **C# format adapters are deferred optional reconciliation, outside required T1–T7.** The source audit identifies foreign layouts to understand reference behavior, not a user request to migrate checkpoint stores. No import/export verbs, Git dependency or Octodiff adapter is required by this plan. If a later concrete migration contract requires adapters, define their exact supported subset and proof separately. Foreign GUID-only states must never authorize Rust resume; leave existing C# stores untouched and diagnose them as foreign rather than silently treating them as Rust data. Choosing CAS instead of Git is an explicit storage representation difference; preserve all required observable history/restore/diff/provenance behavior and record that difference at acceptance.
- Preserve source/game rollback, safe paths and exact hashes. Do not adopt reference weak GUID-only restart trust, checkpoint-error warning-and-continue, missing Git deletion handling, browser reads that create baselines, or unsafe continuation flags. `--no-checkpoint` compatibility may disable retained per-component history **only while keeping existing whole-run recovery and stop-on-error**; document this safety deviation. Best-effort/continue-after-failure aliases must reject for actual installs with actionable rationale, never skip or backfill.
- No new/modified/run Rust tests, inline tests or temporary Rust harnesses. Production builds/Clippy and direct disposable production CLI/native probes only. No protected live game/baseline mutation. One source implementer/compiler owner at a time; independent spec review then quality review per step.

## First bounded deliverable (T1)

A complete **capture → list → verify** production CLI slice for Rust format: capture a baseline of both explicit roots under the existing lock, publish immutable CAS/manifest/session HEAD, list that real checkpoint and verify every referenced object. A second capture may create a new independent baseline session; no invented completed-component prefix. T1 never installs/restores, changes no default engine/UI behavior, and preserves legacy recovery state. Python drivers create small disposable trees, invoke the actual producer, then inspect/corrupt copies to exercise the reader. Hand-authored schema fixtures supplement malformed-input cases only; they are not the primary proof.

This costs the minimal CAS writer and publication path earlier than a read-only slice, but avoids accepting a schema that has never been emitted by its producer and immediately provides useful verified backups. Bound T1 to new baseline sessions, empty completed prefixes, typed capture/list/verify outcomes and safe orphan handling; defer component journal, resume, restore, diff/provenance enrichment and cleanup. T1 is not F11 completion; T2–T7 remain required.

## Persistent format v1

Location: `<recovery::state_dir(roots)>/checkpoints-v1/`, outside game/mod roots, while legacy `snapshot`, `snapshot.json`, `pending`, `completion.json` remain unchanged. Constructor validates but does not create paths. Existing root locks protect every mutator. Storage beneath this directory rejects symlinks/reparse-like path escape, special files, noncanonical IDs, unknown schema versions and malformed objects. No user-authored string becomes an unchecked path. Store roots are fixed by caller `Roots`, not imported JSON.

| Artifact | Fields / rule |
|---|---|
| `objects/sha256/<first2>/<remaining62>` | Raw bytes named by lowercase 64-hex SHA256; verify length/hash before reuse/publication. Copy, never hardlink, mutable live files. Object temporary files live in this same filesystem. |
| `sessions/<uuid>/session.json` | Immutable identity: schemaVersion=1, sessionId, createdUtc, canonical mods/game roots, install scope, original ordered component definitions/selected option payload, parentSessionId/parentCheckpointId, origin (`rust`). Unknown foreign formats are rejected; no foreign schema fields reserved speculatively. |
| `sessions/<uuid>/checkpoints/<uuid>.json` | Immutable schemaVersion/id/sessionId/parentId/sequence; kind Baseline or Component; component GUID/name when applicable; exact completed ordered definition prefix; game/mod tree maps, auxiliary artifact inventory, file counts/bytes; provenance of creator and root bindings. |
| Tree map | Sorted portable relative paths; entry kind Directory or File; files contain sha256 and size, plus supported executable/readonly mode metadata. Preserve empty directories. Reject aliases/case collisions and file-vs-directory ancestors. No symlinks or special files. Cross-platform metadata differences are explicit; no ACL/owner/xattr equivalence claim without later platform evidence. |
| `sessions/<uuid>/HEAD.json` | Single authoritative mutable pointer: schemaVersion, generation, checkpointId, status Ready/Complete, last committed operationId. Parent chain must terminate at baseline, no cycles, monotonic sequence, exact prefix growth. Readers validate referenced metadata rather than trust filenames. |
| `active.json` | Selected sessionId only; convenience selector, never authority for commit or replay. Missing/stale selector cannot create a session or waive validation. |
| `operations/<uuid>.json` | Durable operation intent: InstallComponent or Restore or Finalize or SourceRebase; sessionId, expected generation/from checkpoint, target checkpoint if restore, component definition for pending execution, exact captured roots/auxiliary bindings, phase Intent/Materializing/Verified. Pending operation discovered by scanning this bounded directory, not solely active.json. |
| `trash/`, `.tmp-*` | Uncommitted objects/metadata or deletion staging; excluded from visible history. GC may remove only under locks after proving unreachable from all valid live heads, histories and pending intents. Corrupt metadata halts GC; it is not treated as no references. |

Canonical identity serialization is explicit: recursive JSON object keys sorted lexically, arrays retain order, no whitespace, UTF-8, scalar types preserved. Store full canonical component definitions as well as digests; never rely only on component GUIDs. IDs are parsed UUIDs with canonical filename spelling. Times are UTC RFC3339 informational values, never ordering authority. Paths in root binding use actual canonical OS paths, not lossy conversion; reject unsupported non-UTF-8 JSON bindings explicitly in v1.

## Shared API and ownership boundaries

New `checkpoint/` library owns schema, pure validation/diff, CAS, store/journal, restore and lifecycle operations. Its public read API returns typed `SessionSummary`, `Checkpoint`, `TreeDiff`, `Provenance`, `VerificationReport`; no egui/clap types. Public write operations take a typed cancellation token and emit typed progress; no renderer infers commit success.

- `Store::open(&Roots) -> Result<Store>` is read-only, including when absent. `list`, `inspect`, `diff`, `verify` never mkdir, lock-create, repair, hash current live roots unless explicitly requested, or follow unsafe links. Each command reads immutable documents and an atomic HEAD snapshot; report generation and stale-head detection if it changes. Missing store means empty list; malformed present store is an error.
- Write entry obtains `recovery::Lock::acquire` once. Engine passes an internal nonforgeable held-lock capability into checkpoint methods; no reacquisition/deadlock. Extend lock visibility narrowly; no public unlocked mutator. Cross-root auxiliary artifacts use the same deployment lock order agreed in T3, not an independent lock grabbed after mutation.
- `begin_session`, `begin_component`, `commit_component`, `restore`, `recover_pending`, `resume_plan`, `complete`, `delete_session`, `gc`, `repair` are library methods. Exact Rust signatures belong to implementer after T1 review; required semantics here are fixed.
- `resume_plan(guide, checkpoint)` validates roots and exact completed prefix, returns only the ordered suffix plus verified shared context. It does not execute or mark success. Shared engine consumes that result; CLI cannot manually splice IDs around engine validation.
- Provenance reports checkpoint/parent/component identity and per-path add/change/delete history with source hashes, including source root. It is evidence about captured effects, not guessed causal attribution to individual patcher internals.

CLI namespace: T1 `checkpoint capture`, `list`, `verify`; T2+ `inspect --session --checkpoint`, `diff --from --to`, `restore`, `recover`, `resume`, `delete-session`, `gc`, `repair`. No import/export verbs are planned. All require explicit game/source roots; selection flags and existing phase preparation are reused for resume. JSON results include schemaVersion, operation, session/checkpoint/generation and outcomes; diagnostics stderr and nonzero failure, 130 cancellation. Mutations never print success before verified publication. Exact text/JSON goldens are direct CLI receipts, not Rust tests.

## Crash and commit state machine

Write all new object and metadata files to private siblings, flush data with sync_all, publish no-clobber, then sync parent directory using supported platform implementation. HEAD replacement similarly writes+flushes then atomically replaces+syncs. Never overwrite an existing immutable artifact, even if content differs only cosmetically. Implement platform durability helpers deliberately; before native evidence, claim only tested process-interruption semantics, not universal power-loss guarantees. Unsupported atomic replacement/directory flush must be classified and handled explicitly, never silently called durable.

**Baseline:** capture both roots and auxiliary artifacts under locks; capture before/after manifests to detect changes by noncooperating writers; hash stored content independently. Publish objects, baseline checkpoint, session metadata, HEAD, then selector. A partial session with no valid HEAD is nonexecutable, inspectable as incomplete. Baseline failure happens before install mutation.

**Component N:** validate clean state and input → publish durable InstallComponent intent bound to current HEAD → execute N → capture/verify both resulting roots and auxiliary state → publish immutable checkpoint → atomically advance HEAD generation → remove intent and sync operations directory → only then emit ComponentCompleted or begin N+1. Any capture/publication failure stops with intent retained. If interrupted after HEAD advance but before intent deletion, recover identifies matching operationId and verifies HEAD/live state before finalizing cleanup; otherwise restore old HEAD. Unreferenced checkpoint metadata is an orphan, never proof N completed.

**Selected or failure restore:** prevalidate complete target closure and root binding before deleting anything; capture a safety baseline of current roots for user-selected rollback when no failed operation already protects them → publish durable Restore intent → materialize target files via temporary sibling files and verified copies, remove paths absent from target, restore directories/modes, preserving root inodes → verify exact two-root inventory and auxiliary manifest → publish HEAD/receipt reconciliation → mark intent Verified then remove. Cancellation or crash leaves intent fenced. `recover` resumes idempotent materialization of the same target, never installs into a half-restored tree. Missing/corrupt target object prevents all destructive work at initial preflight; later I/O failure preserves intent and reports partial materialization honestly.

**Final completion:** durable Finalize intent binds final HEAD and expected legacy completion payload; write legacy completion receipt and clear legacy pending only after final checkpoint verified; set HEAD Complete with operationId; clear intent; emit Completed. On restart, reconcile or restore from intent. Reader `ensure_clean` checks new pending operations as well as legacy pending, so clearing one cannot permit install while the other remains unresolved.

Delete/GC first protect active sessions, current ancestry and pending-intent targets. Logical session deletion uses same-filesystem rename into trash under lock then directory sync; retain objects until a fresh reachability scan. Repair may recover only from bytes that match expected hash (other store object or verified live file), never rewrite expected hashes to make corruption pass. Publish repaired bytes and reverify; retain diagnostic history.

## Resume, source repair, phases and managed effects

- Resume requires exact current game/mod inventories matching selected checkpoint and an unchanged completed definition prefix. Full guide suffix can change to fix N, provided topological preparation retains exactly the committed prefix and no new/reordered prerequisite enters it. New suffix definitions are recorded in a branched session; preserve original history. Duplicate IDs, prefix deletion/reordering or changed committed option payload reject.
- Source archive repair is allowed **after** successful restore. `resume --accept-source-changes` reports changed mod-root paths/hashes and captures a SourceRebase branch baseline; game/prefix/auxiliary state must remain identical. Without the flag, changed mods reject. This authorizes source changes for the new attempt, not installation skipping or retroactive mutation of prior checkpoint identity. The flag is a concrete CLI intent, not a new interactive approval requirement.
- Base/Remaining share existing `phase::prepare` and receipt checks. A Base success remains a verified prefix; Remaining creates a linked session with its own baseline and ancestry, retaining original Base definitions. Restoring an earlier point invalidates/rebuilds legacy completion according to that point; no stale Base receipt survives contradictory bytes. A prefix of zero clears the receipt.
- Managed deployment writes outside game/mod roots. T3 must register exact session-owned manifest/staging/owner artifacts as auxiliary transactional roots, capture existence/bytes and restore them coherently under deployment locks. Never permit checkpoint-enabled managed execution without this participant contract. Foreign profile data not owned by the session is not blindly restored. Changes in source roots, artifact roots or profile binding reject resume.
- Peer sharing/acquisition must quiesce before capture/install/restore to prevent concurrent source writes. Locks alone do not stop external patchers or arbitrary filesystem writers: detect changed captures and abort; do not claim protection from hostile concurrent writers.

## Legacy compatibility and rollout

T1–T2 add operations only. Existing `recovery::{begin,finish,restore,completion_summary}` and default install behavior remain intact. T3 adds an additive engine entry/configuration for component checkpoints with shared CLI flag; default remains whole-run until T4 proof/review. Legacy pending snapshots always remain restorable with `restore`; no auto-conversion/deletion. New intent takes precedence if both exist; checkpoint recovery reconciles legacy pending before any fresh install.

T4 enables component checkpoints by default only after required boundary/restore probes pass and both frontends consume the shared default. Keep whole-run baseline as compatibility fallback during migration; storage budgets account for its temporary duplicate cost. A legacy restore performed during a new session must mark the new session detached and reconcile pending intents under the same lock, or refuse with `checkpoint recover` guidance; it must not leave executable stale HEAD. Old consumers remain able to read legacy completion after fully committed success. Migration never trusts an old completion as a per-component checkpoint without capturing and verifying its current roots.
