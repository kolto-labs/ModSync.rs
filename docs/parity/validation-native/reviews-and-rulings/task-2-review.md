## Specification verdict: CHANGES REQUIRED

### [P2] Keep validation controls enabled on the small-window route

`src/ui.rs:2803-2818` sends the large layout directly to `validation_content`, but the fallback goes through `wizard_content`. That method at `src/ui.rs:537` disables its entire child UI whenever a worker is running. Consequently the page's Stop button (`src/ui/validation_page.rs:255`), expander and scroll/splitter controls become disabled precisely during validation in the supported smaller layout. The global Activity Stop is also removed while Validation is visible. Closing the window can still trigger a confirmation; it is not a substitute for the page Stop control. Fix by keeping this dedicated page outside the blanket idle-only wrapper at every size while preserving explicit per-action gating. Require a direct small-window in-flight Stop/log interaction observation, without new Rust test code.

### [P2] Clear page presentation whenever the underlying validation is discarded

`src/ui.rs:2063-2073` begins/reset page state only for `Job::Validate`, then clears `validated` and `validation_report` for every job. Non-validation operations such as the direct sidebar Download leave `validation_page.completed` and its old `view` intact. `src/ui/validation_page.rs:385-397` renders that old Passed summary/cards but draws zero counters from the now-absent report. `reset_installation` at `src/ui.rs:1524-1533` also clears the report without the new page state, allowing stale presentation on a same-guide restart with an unchanged input stamp. Navigation stays fail-closed, but the visible validation outcome contradicts readiness and data validity. Centralize presentation invalidation with report invalidation; preserve an active validation begin/reset where appropriate. Demonstrate a validated page followed by a non-validation job/reset returns to truthful initial or invalidated presentation.

### [P2] Prevent the empty-progress header from overlapping its controls

`src/ui/validation_page.rs:277-295` lays out the expander button, unconditional progress label and hint in `horizontal_wrapped`. When setup fails before any progress, the empty progress/header layout places the hint over the toggle. This is directly visible in final-bound `/tmp/modsync-rust-validation-task2/acceptance-setup-failure.png`: “Drag the splitter below to resize” overlaps “Validation Log” at 1280x800. Preserve a real horizontal allocation for present elements and skip/layout empty progress safely. Reobserve setup failure and an early running frame after correction; the error details and disabled navigation must remain intact.

### [P2] Use distinct pinned theme tokens for log borders and button interaction states

`src/ui/validation_page.rs:178-215` conflates generic border and button colors. Pinned C# K1 `Styles/KotorStyle.axaml:47` sets generic Border to `#3AAAFF`, whereas Rust uses button border `#062766` for the log border. K2 `Styles/Kotor2Style.axaml:47` sets generic Border `#18AE88`, but Rust uses `#0A2A22`; the K2 button template border is `#0D5945` (`:71`), not `#0A2A22`. K2 hover border is `#E0F2F1` (`:75`), while Rust uses the pressed-state `#3FE6C0`. The unconditional `override_text_color` at line192 also prevents source-required K1 yellow `#A8B348` and K2 near-white `#F2F2F2` hover foregrounds, and the dark hover backgrounds are replaced with `border` rather than the pinned backgrounds. These are source-established differences from the explicit matched-theme contract, independent of font metrics or native screenshot tolerance. Use separate surface/button/hover/pressed tokens and per-widget text styling, then observe Light/K1/K2 hover and disabled states. Do not broaden this fix into unrelated shell redesign.
