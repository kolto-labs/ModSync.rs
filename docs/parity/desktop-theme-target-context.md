# Desktop theme and target context

Explicit guide TargetGame metadata (nested metadata first, then root keys) owns
presentation identity. Settings-derived theme identity is a fallback only when
that key is absent. K1/KOTOR1 and TSL/KOTOR2 are recognized without case sensitivity,
matching the reference's accepted target identifiers. Explicit empty, non-text,
or unknown target values do not inherit a settings game; they produce neutral
presentation. This does not authorize installation or replace installed-game
recognition.

The desktop synchronizes this context after settings polling and worker messages.
Recognized authored target games choose KotorStyle/Kotor2Style. Without guide
authority the stored theme remains the presentation preference. The same resolved
target controls conditional AspyrNotice placement when warning content exists.

`Wizard::apply_target_context` is additive: it updates only the conditional notice,
preserves the current page when still present, and returns to GameDirectory if the
current notice disappears. Existing constructors/reset signatures and behavior
remain available. Dynamic widescreen state is preserved. No guide metadata or
persisted theme is changed by this presentation synchronization.

## Encoding audit

Pinned `ModComponentSerializationService.SanitizeUtf8` receives an already decoded
.NET string. It chooses FileEncoding, calls GetBytes for each UTF-16 code unit,
then appends the original character; it never decodes those generated bytes.
Configured encodings use their normal replacement fallback (UTF-8 explicitly
uses throwOnInvalidBytes=false), so unsupported characters ordinarily do not cause
the exception branch that skips them. This is not a legacy-byte decoding layer.
Pinned FileLoadingService normally reads bytes and applies nonthrowing UTF-8
GetString followed by replacement-character-to-underscore substitution.
File.ReadAllText is only its exception fallback and does not receive FileEncoding.
Rust Guide loading likewise decodes UTF-8 lossily and replaces replacement
characters with underscores; the displayed compatibility
encoding field is not evidence that a missing configured-codepage decoder exists.
Malformed-byte handling and BOM behavior are separate loader acceptance questions,
not a justified new locale preference or encoding-setting consumer.

Evidence is source inspection and targeted formatting only. No tests, builds,
runtime desktop checks, encodings probes or CI actions were performed.
